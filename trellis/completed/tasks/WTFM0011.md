# WTFM0011 - Build WTFM's real documentation site and Taproot Docs artifact

WTFM0010 added and released the opt-in Taproot Docs artifact emitter, but this
repository still has no real documentation project. Its conformance fixture
proves the emitter contract; it is not product documentation and must never be
published as the WTFM site.

Build an actual WTFM documentation site so Taproot TR00589 can close and
TR00588 can publish honest WTFM content through the local release/stage/serve
flow.

## Scope

- Add a maintainable Eleventy documentation project under `docs/` containing
  substantive WTFM product documentation. Cover at least:
  - installation and basic Eleventy setup;
  - plugin configuration;
  - authored documents and reference surfaces;
  - Taproot Docs artifact mode;
  - renderers and semantic-output constraints;
  - help documents, manifests, and anchor validation;
  - client runtime and code-block behavior;
  - validation and troubleshooting.
- Configure the project through the working tree's
  `src/server/eleventy-plugin.js`. Do not add `@taprootio/wtfm` as a dependency
  of itself or pin the docs to a previously released WTFM version.
- Keep `@taprootio/docs-artifact` pinned at exactly `1.0.1` as the external
  artifact contract.
- Enable `taprootDocs` so one build produces both the ordinary portable site
  and `taproot-docs-manifest.json` plus the declared `taproot-docs/` semantic
  artifact.
- Use explicit stable resource keys, navigation, headings, redirects,
  provenance, source paths, and source links derived from real repository
  content. Keep all conformance-fixture content out of the product site and
  artifact.
- Bind artifact provenance to GitHub repository id `1162327960`, repository
  `taprootio/wtfm`, ref `refs/heads/main`, and the checked-out Git `HEAD`
  revision. Resolve both revision and commit epoch locally and fail closed when
  deterministic Git provenance is unavailable.
- Use `docs/_site/` as the one deterministic output and artifact directory.
  Generated output and Eleventy caches remain ignored.
- Add convenient documented package scripts for building, validating, and
  testing the real docs project. Validation must call the released
  `@taprootio/docs-artifact@1.0.1` validator rather than duplicating schema
  logic.
- Keep the ordinary static site accessible and portable without the Taproot
  semantic payload. It must not depend on a Taproot environment, site, runtime,
  or publishing configuration.
- Keep the existing WTFM0010 fixture as focused emitter conformance coverage;
  do not copy or expose fixture content as product documentation.
- Do not publish the artifact, create a Taproot site or key, call a Taproot
  environment, add GitHub publishing workflows, or change production/local
  infrastructure. Those belong to Taproot TR00588/TR00485.

## TDD and verification

- First add focused behavioral tests that fail because the real documentation
  project and commands do not yet exist, before adding production docs files.
- Prove a clean checkout can build the real static site and schema-v1 artifact
  using the documented commands and the working tree's local implementation.
- Validate through `@taprootio/docs-artifact@1.0.1` and prove repeated builds
  from identical source inputs produce byte-identical manifest/artifact output.
- Prove the artifact identifies `taprootio/wtfm`, uses repository id
  `1162327960`, and contains substantive real documentation resources rather
  than conformance-fixture content.
- Prove the build initiates no network request or publishing operation, using a
  process-level network guard around the actual docs build.
- Prove ordinary site HTML, navigation, links, styles, and assets remain usable
  independently of the semantic payload.
- Keep `npm run build`, the complete WTFM test suite, the docs build and
  validator, and `npx @taprootio/trellis check` green.

## Notes

- The product documentation may use authored `guide:`, `concept:`, and
  `reference:` resources to explain WTFM's reference-surface APIs. It must not
  manufacture a component surface solely to imitate the conformance fixture.
- `npm run docs:build` is the canonical build command.
- `npm run docs:validate` is the canonical artifact validation command.
- `docs/_site/` is the directory Taproot TR00588 should consume.
- Cross-repository handoff: this task fulfills Taproot TR00589. Taproot TR00588
  remains responsible for consuming and publishing the artifact.

## Risks

- Git-derived provenance must remain explicit at the plugin boundary and fail
  closed instead of silently describing unrepresentable source.
- Product Markdown must obey both Eleventy's full-site rendering rules and the
  Taproot Docs closed semantic markup contract.
- A visually navigable site can still be non-portable if links or assets depend
  on the semantic payload; focused link and asset checks must exercise the
  ordinary output independently.
- Tests must detect network-capable behavior without adding a publisher,
  credential, site id, or environment-specific configuration to the repository.
